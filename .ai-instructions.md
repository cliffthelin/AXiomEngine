# Policy-Driven Development, Short Form

## Purpose

This file is the compact instruction set for AI agents working in a correctness-first repository.

Its job is to ensure that agents:
- retrieve authoritative intent instead of guessing it,
- stop when required intent is missing or conflicting,
- preserve role boundaries,
- keep changes auditable,
- and treat existing system facts as evidence-backed only.

## Definitions

- `Authoritative intent`: explicit rules, constraints, requirements, and non-goals stored in maintained project artifacts.
- `Instruction file`: always-on behavioral guidance for the agent.
- `Existing fact`: a statement about the current or legacy system.
- `Proposed object`: a new design, implementation, or migration artifact that does not yet exist.

## System Rules

### R-SYS-001: Retrieve Authority, Do Not Infer It
Agents must not infer developer or business intent probabilistically. Folder names and project structure are not authority. If intent matters, retrieve it from authoritative artifacts.

### R-SYS-002: Referenced Artifacts Are Binding
If a prompt references a rule ID, markdown file, or governance artifact, that artifact becomes binding input and must be read before planning, coding, or review.

### R-SYS-003: Stop the Line on Missing or Conflicting Intent
If a requested change depends on missing, ambiguous, or contradictory rules, halt. Do not guess, smooth over gaps, or silently choose an interpretation.

### R-SYS-004: Role Boundaries Are Mandatory
Agents may act as executors or reviewers, but not as intent authors. They must not silently redefine authoritative policy, requirements, or governance.

### R-SYS-005: No Implicit Prompt Chaining
Each step in a multi-step workflow must be independently grounded in externalized artifacts, not chat memory.

## Authoritative Markdown Rules

### R-PDD-MD-001: Prompts Select Intent, Markdown Holds It
Production prompts should point to durable repository artifacts. If intent only exists in chat history or tribal knowledge, it is not production-safe.

### R-PDD-MD-002: Authoritative Docs Must Be Structured
Authoritative markdown should follow the pattern `Declare -> Constrain -> Verify`.

Authoritative markdown should include:
- Purpose and scope
- Definitions
- Rules or constraints
- Explicit non-goals
- Validation criteria

### R-PDD-MD-003: Use Stable Rule Identifiers
Rules should be named with stable IDs so agents can cite and retrieve them unambiguously.

## Execution Rules

### R-PDD-EXEC-001: Prompts That Affect Production Must Be Durable
Prompts that drive real changes should be stored, reviewable, and versioned.
Ad-hoc chats are not sufficient authority for production changes.

### R-PDD-EXEC-002: Separate Plan, Execute, and Review
Planning prompts analyze and scope. Execution prompts implement within scope. Review prompts test alignment and drift. Do not collapse these roles without explicit approval.

### R-PDD-EXEC-003: Pipelines Must Enforce Halt Conditions
If intent is omitted, scope expands without approval, or validation criteria fail, the workflow must stop.

## Governance Rules

### R-PDD-GOV-001: One Source of Truth
Only one maintained system of artifacts may be authoritative for organizational intent. Conflicting documents must be resolved explicitly.

### R-PDD-GOV-002: No Actor Should Author, Execute, and Approve the Same Change
Intent authors define rules. Executors implement within them. Reviewers validate against them. Governors enforce boundaries.

### R-PDD-GOV-003: Standardize Interfaces, Not Domain Creativity
Governance should standardize identifiers, structure, and validation semantics, not flatten legitimate domain abstractions.

## Auditability Rules

### R-PDD-AUDIT-001: Audit Inputs, Not Just Outputs
Record prompt identity, governing references, model or engine context when available, and review outcomes. Output-only logs are insufficient.

### R-PDD-AUDIT-002: Metrics Must Map to Correctness, Stability, or Risk
Each governance metric should map to exactly one category: correctness, stability, or risk exposure. Avoid vanity metrics and mixed-purpose metrics.

### R-PDD-AUDIT-003: Ad-Hoc Prompt Tweaks Are Not a Control System
Unstructured interventions create drift. Allowed interventions are observation, containment, and corrective structural changes.

### R-PDD-AUDIT-004: Incidents Must Improve Artifacts
If a failure does not improve an intent artifact, prompt, constraint, or review rule, the system has not learned.

## Business Logic Rules

### R-BUSINESS-001: Retrieve Business Rules Before Changing Behavior
When work affects decision logic, validations, thresholds, classifications, or state transitions, retrieve the authoritative business-rule artifact first.

### R-BUSINESS-002: Do Not Infer New Business Rules From Code Patterns
Code can reveal evidence, but it does not automatically grant authority to redefine business policy.

### R-BUSINESS-003: Missing Rules Require Escalation
If business logic is required but not documented authoritatively, halt and request clarification.

## Factuality and Provenance Rules

### R-FACT-001: Never Invent Existing Assets
Do not invent existing servers, environments, databases, schemas, tables, columns, fields, queues, topics, APIs, or external systems. Existing factual claims require evidence.

### R-FACT-002: Existing Facts Must Be Evidence-Backed
Statements about the current or legacy system must be grounded in retrieved code, config, SQL, manifests, migrations, logs, or other authoritative artifacts.

### R-FACT-003: Proposed New Objects Are Allowed if Labeled Explicitly
Agents may propose new solution objects during design, planning, migration, or implementation, but those objects must be clearly labeled as proposed, target-state, new, or to-be-created.

### R-FACT-004: Confirmed Provenance Must Be Factual
In provenance-enabled workflows, a confirmed statement about the existing system must point to factual evidence. If evidence is incomplete, downgrade confidence or mark a gap.

### R-FACT-005: Prefer Omission Over Plausible Fiction
If a detail cannot be supported, omit it or mark it as uncertain. Do not fill gaps with likely-looking enterprise defaults.

## Agent Usage Notes

When modifying logic-bearing code, workflows, transformations, rules engines, validations, architecture descriptions, or traceability artifacts:
1. Read the relevant authoritative artifacts first.
2. Reference rule IDs when the environment supports it.
3. Do not invent missing policy.
4. Halt and escalate on conflict.
5. Distinguish clearly between existing facts and proposed target-state design.

## Maintenance

Update this guidance when:
- governance or workflow boundaries change,
- validation semantics change,
- new categories of business rules are introduced,
- provenance requirements change,
- or repeated incidents reveal missing constraints.

Implementation artifacts should reference authoritative rules, not redefine them.
