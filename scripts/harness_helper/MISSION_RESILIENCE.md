# MISSION RESILIENCE RETROSPECTIVE

## 🛑 Problem: The Stalled Swarm
During the initial 10-hour autonomous block, the Governance Swarm encountered three critical failure modes that led to a complete mission stall. 

### 1. The Schema Drift (Missing 'source' key)
*   **Root Cause**: The rule ingestion pipeline merged data from `TargetedDiscovery` (Markdown-based) and `ExhaustiveDiscovery` (Grep-based). The latter lacked a `source` field, causing a `KeyError` during logging.
*   **Impact**: Mission crash.
*   **Prevention**: Implementation of `G-AXIOMENGINE-RESILIENCE-DATA-ROBUST-001`. Always use `.get()` for dictionary access in telemetry and logging layers.

### 2. The Semaphore Scope Failure
*   **Root Cause**: The `asyncio.Semaphore` was correctly initialized but incorrectly scoped—it only protected the timestamp generation, allowing 500+ concurrent AI requests to fire simultaneously.
*   **Impact**: GPU/VRAM saturation and 100% request timeout.
*   **Prevention**: Implementation of `G-AXIOMENGINE-RESILIENCE-SEMAPHORE-001`. Ensure the `async with semaphore` block wraps the *entire* heavy-compute coroutine.

### 3. The Synchronous Event Loop Block
*   **Root Cause**: Using `urllib.request.urlopen` (a blocking synchronous call) inside an `async` function without offloading to a thread. This effectively serialized the entire "parallel" swarm.
*   **Impact**: Throughput dropped to 1 rule/batch-time (deadlock-like behavior).
*   **Prevention**: Implementation of `G-AXIOMENGINE-RESILIENCE-ASYNC-001`. Use `asyncio.to_thread()` for all blocking I/O (network, disk, subprocess).
